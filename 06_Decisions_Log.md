# Decisions Log

## Major Decisions

### Keep Qwen2.5-0.5B

Reason: Fast local inference.

### Rewrite build_dataset.py

Reason: Dataset quality was the primary issue.

### Audit before retraining

Reason: Never retrain blindly.

### Prefer concise responses

Reason: Reduced hallucinations.

### Remove unused scripts

Deleted `generate_dataset.py` (superseded by build_dataset.py,
referenced a field that no longer existed - broken), `infer.py`
(empty file), `augment_questions.py` (output never consumed by
train.py).

Reason: Dead code with no consumers; kept the pipeline confusing
about which script is the real one.

### Add a dedicated AsciiDoc parser for Git docs

Reason: Git's Documentation folder is AsciiDoc, not Markdown. The
original pipeline only read `*.md`, so git-docs silently contributed
zero training examples despite being cloned and configured -
discovered by checking category counts by source, not by any error
message.

### Restrict Git indexing to top-level Documentation/ only

Reason: Subfolders (`RelNotes/` - 542 version changelog files,
`config/` - config-key fragments, `howto/`, `technical/`) are not
command references and were producing junk `commands.json` entries
(e.g. a "command" literally named after a version number).

### Restrict PowerShell indexing to real cmdlet reference folders

Reason: `reference/docs-conceptual` (638 files) contains style-guide
and language-reference articles, not cmdlet docs - same category of
problem as the Git RelNotes issue.

### Add Linux source via tldr-pages, then curate it

Initial version pulled the entire tldr `common`/`linux` tree
(~6,600 commands), producing 113,348 examples. A spot check showed
much of it was irrelevant to IT operations (desktop apps, games,
niche dev tools).

Reason: Curated down to an explicit allowlist of ~200 real sysadmin
commands (file/text processing, process & service management,
networking, permissions, disk, package managers, containers, ssh).
Volume is not the same as value - matches the existing "dataset
quality over quantity" lesson from the original build_dataset.py
rewrite.

### Add an "intent" category, generated by template not LLM

Reason: The stated goal is for the model to map a user's described
goal to a command recommendation, not just answer "what does X do."
Chose templates derived from real doc text (tldr's own bullets, git's
title structure, PowerShell's synopsis) over LLM generation, because
the two previously-deleted LLM-based generator scripts in this
project were themselves abandoned/broken - template-based extraction
has been the more reliable pattern here.

### Fix code-fence collision bug in example generation

Reason: Git/Linux commands were tagged ```` ```text ```` in code
blocks, which build_dataset.py's output-cleaning step strips
(intended to remove terminal output dumps, not commands). This
silently deleted the actual command from every git/Linux example
answer. Re-tagged as ```` ```bash ````.

### Speed up training via batch size, not step count

Reason: Benchmarked before touching train.py - GPU was underutilized
(only 1.96GB of 8.6GB VRAM used) because batch_size=1 processed
examples one at a time. Raised per_device_train_batch_size to 8 and
dropped gradient_accumulation_steps to 1, keeping effective batch
size (and therefore step count and training math) identical - ~10x
projected speedup with zero change to what the model learns. Also
disabled gradient_checkpointing since VRAM headroom made its
memory-for-compute tradeoff unnecessary.

### Add 6 phrasing variants per parameter question, plus a new "overview" category

Reason: user reported "grep -i" worked but "grep i" (no dash) failed
- the model had only ever seen one rigid phrasing per flag. Also
added an "overview" category ("list all X flags") since no question
shape existed for that at all. Applied dataset-wide via template
(no LLM), not just to grep.

### Add Windows keyboard shortcuts as a new source

Reason: user directly requested it ("F2 ne yapar" failed). No git
repo exists for this; sourced from Microsoft's official support page
via WebFetch, saved locally, added a new `shortcut-list` parser
format (one file -> many records, a new architectural pattern).

### Run a 3-epoch training experiment, then abandon it

Reason: hypothesized more epochs would fix exact-recall gaps
(overview, shortcuts) that 1 epoch didn't cover. Result was negative
- didn't fix the target problem and regressed previously-correct
answers (see 03_LoRA_Training.md). Kept as a documented negative
result rather than deleted, since it directly informed the decision
to pursue RAG instead of more training.

### Adopt RAG instead of continuing to chase exact-recall via training

Reason: the 3-epoch experiment was strong evidence that a 0.5B LoRA
(r=16) cannot reliably memorize hundreds of exact multi-fact answers,
regardless of epochs or phrasing diversity - this is a knowledge
problem, not a behaviour problem (matches the "LoRA teaches
behaviour, RAG supplies knowledge" strategy already written below,
just arriving sooner than the roadmap expected). Built with
`sentence-transformers` + brute-force cosine similarity over
`dataset.jsonl` - no vector database needed at ~46K records. Chose
direct-display of retrieved answers over having the LLM rephrase
retrieved context, to keep zero hallucination risk on the categories
that most needed it.

### Add GNU coreutils as a complete-reference source

Reason: user explicitly rejected incomplete flag listings ("eksik
istemiyorum ... eksik kalmayacak"). Root cause of the incompleteness
wasn't a parsing bug - tldr-pages is fundamentally a curated-examples
cheatsheet, not an exhaustive reference (grep's tldr page shows 8
examples, not its ~30 real flags). No source improvement in the
world fixes that without a different source. Chose GNU coreutils'
texinfo manual as phase 1 (one repo, one format, covers ~100
commands including `ls`/`cp`/`mv`/`chmod`/`df`) over trying to
source every tool family at once - explicitly scoped as a first
phase, not a complete fix (grep, ssh, systemctl, docker, package
managers still pending, each from a different upstream project).
Merged coreutils records with matching tldr records (coreutils'
complete parameters + tldr's real examples) rather than leaving both
as separate, potentially-conflicting entries for the same command.

### Add GNU grep as a second complete-reference source

Reason: same rationale as coreutils - tldr's grep page has 8 example
bullets, not grep's ~30 real flags. GNU grep publishes its own
texinfo manual using the standard `@table @option`/`@item`/`@itemx`
convention (different from coreutils' custom `@optItem` macro), so it
needed its own parser (`extract_gnu_table_parameters`) rather than
reusing coreutils' - same depth-tracking design once the nested-table
bug (below) was found and fixed in both.

### Rewrite texinfo option-table parsing as a depth-tracking parser

Reason: the original `@table @samp(.*?)@end table` non-greedy regex
assumed option tables never nest. `nl`'s texinfo section has a SECOND
`@table @samp...@end table` pair inside one option's own description
(illustrating a format choice) - the regex matched the wrong, inner
`@end table` and silently dropped every flag documented after it (9
of `nl`'s 11 flag pairs vanished with no error). Rewrote as a
line-by-line parser that tracks nesting depth explicitly; only a
depth-1 `@end table` ends the real option block. Applied to both the
coreutils and grep parsers.

### Generalize option-borrowing beyond the checksum family

Reason: `dir`/`vdir` don't document their own options either - same
"no native documentation" pattern already handled for
`md5sum`/`b2sum`/`sha1sum` (which borrow from `cksum` via a checksum
macro), just via a different in-doc mechanism (`@xref{ls invocation}`
instead of a checksum macro). Generalized the existing
checksum-specific logic into `borrows_from`: any command with an
`@xref{X invocation}` reference and no parameters of its own copies
`X`'s parameter list.

### Tag every dataset row with its source `command`, add
    command-scoped retrieval

Reason: found live that "what does the -w flag do in printf?" (printf
has no `-w`) confidently returned `od`'s or `pr`'s real `-w` data
instead of admitting printf has no such flag - nothing in retrieval
verified the matched record's command matched the one named in the
query. Fixed at the data level (every row now carries its source
`command`) and the retrieval level (`test_model.py` detects the
command named in a flag question via word-boundary-safe matching,
restricts search to only that command's records, and returns an
honest "no data" answer if that command has zero flag data - never
silently falls back to a different command's answer). See 07_RAG.md.

### Add case-sensitive exact-match routing for no-dash flag questions

Reason: 107 (command, letter) pairs in the dataset have genuinely
different meanings for the lowercase vs. uppercase form of a
no-dash, casual-phrased question (`"ls l"` = long format, `"ls L"` =
dereference symlinks) - the embedding model barely distinguishes
single-letter case, so these were resolving inconsistently/wrong.
First attempt anchored bare-flag detection to the literal generation
template ("X do?"/"X ne yapar?") - too narrow, missed freeform
phrasing like "how can i use grep E". Final fix checks the word
immediately after the mentioned command against that command's
actual known bare-flag set (built from the dataset itself), which
works regardless of sentence structure while still rejecting
unrelated words ("how does chmod work" doesn't falsely trigger,
since "work" isn't one of chmod's real flags).

### Add a general texinfo macro-expansion pass

Reason: manually auditing `dirname`/`printenv` (both showed 0
parameters, looked suspicious) revealed they each define their one
real option via a shared macro call (`@optZero{dirname}`) instead of
literal `@optItem{...}` text - the parser only recognized the literal
form. Checking how many other commands share this pattern found ~20
such macros used across 33 commands total (`cp`, `mv`, `ls`, `chmod`,
`head`, `tail`, `sort`... - not a niche edge case). Wrote a general,
recursive macro-expander (handles macros that call other macros) that
runs before section-splitting, deliberately stopping short of
expanding `@optItem`/`@optItemx` themselves so the existing
depth-tracking parser didn't need to change at all. Recovered 276
parameters.

### Remove the bogus "Multi-call" command entry

Reason: `@node Multi-call invocation` is a documentation section
about coreutils' multi-call binary mechanism, not a real utility -
the section-splitting regex captured "Multi-call" as a command name
anyway, and its description came out corrupted (an unrelated `@menu`
list leaked in). Fixed by comparing the split-out node name against
the real `@command{X}` name found in the section's own `@section`
line; only this one section disagreed, so it's the only one filtered
out - a general check, not a hardcoded name, kept it robust to future
doc updates.

### Add Docker CLI and systemd as complete-reference sources

Reason: same tldr-incompleteness rationale as coreutils/grep, applied
to two more tool families the user explicitly prioritized (agreed
sequence: Docker first as easiest/highest-value, systemd next, ssh
last as hardest). Docker's own `docker/cli` repo publishes a
generated Markdown reference (one file per command, regular flag
tables) - easier to parse than any texinfo source so far. systemd
publishes its own DocBook XML manual - chose a curated 16-file
allowlist (CLI tools + the most-used unit-file directive references)
out of 484 total files, mirroring the coreutils/linux-docs curation
pattern rather than ingesting everything (most of the 484 are
internal D-Bus/API docs irrelevant to an IT-ops assistant).

### Fix coreutils description quality (dangling sentences, leaked
    `@menu` syntax, nested-macro `@xref` bug)

Reason: while manually checking a "tail" answer at the user's
request, found it trailed off mid-sentence ("...consisting of:" then
nothing) - traced to `@example` blocks being stripped without also
removing the sentence that introduced them. Checking for the same
bug class found it wasn't just `tail`: `@menu` blocks (texinfo's
table-of-contents syntax) were never stripped at all and leaked raw
into multi-subsection commands' descriptions (`ls`, `join`, `ptx`),
and a separate bug let nested macros break `@xref` stripping when a
macro like `@command{printf}` appeared *inside* an xref's own
arguments (leaving raw reference text and a stray `}` in `printf`'s
description). Fixed all three; the dangling-sentence fix specifically
needed a second pass after an early version mistook the "." in
`~/.bashrc`-style filenames for a sentence boundary and cut two
commands' descriptions off mid-word.

### Scope the docker-alias-fanout dedup fix to `docker-docs` only

Reason: `docker build` is documented twice (`builder_build.md` and
`image_build.md`, both resolving to the same short alias) and needed
a "keep the richer one" dedup step. The first version of this fix
matched by `(command name, source)` generically across the *whole*
dataset - which immediately collapsed PowerShell's intentional
multi-version cmdlet records (the same cmdlet documented separately
per PowerShell version, 5.1 through 7.7) from 2,438 down to 585,
caught only because per-source record counts were checked right
after. Rewrote to only touch `docker-docs` records, leaving every
other source's same-name records (including deliberate cross-platform
duplicates like Windows `dir` vs. GNU `dir`) untouched.

### Generalize systemd's option-parsing away from section-title
    matching

Reason: unlike coreutils (which almost always titles its option
section "Options"), systemd's DocBook manual names sections
inconsistently per page - `journalctl` splits options across "Source
Options"/"Filtering Options"/"Output Options"/two more; `systemd.exec`
organizes its ~200 directives under purely thematic titles ("Paths",
"Sandboxing", "Scheduling"...) with the word "Options" nowhere in
sight. Title-matching would have needed an ever-growing allowlist of
title strings. Instead, scan the whole document for `<varlistentry>`
elements directly and classify each by what tag its `<term>` contains
(`<option>`/`<varname>` = a real flag or unit-file directive;
`<command>` = a subcommand, not a flag) - works regardless of what the
enclosing section happens to be titled.

### Audit already-cloned sources for silent parser gaps before adding
    a new source

Reason: asked to add networking/scheduled-tasks/firewall coverage,
started by checking what already existed rather than immediately
cloning something new - found `windows-docs` already contained ~869
classic Windows CLI command references (`netstat`, `schtasks`,
`netsh`, `robocopy`, `attrib`, `ping`...) that were already being
indexed and parsed, just silently producing zero parameters each,
because their Markdown uses a parameter *table* instead of
PowerShell's `### -ParamName` subheading convention and the existing
parser only recognized the latter. Added a fallback table extractor
instead of sourcing anything new - recovered 4,793 parameters, more
than every other single source addition in this project. Found and
fixed four more bugs surfaced while building this fallback: the same
escaped-pipe-breaks-table-split bug already known from Docker
recurred in `attrib`'s option syntax; a variant of it (unescaped pipe
tolerated inside backticks by GitHub's renderer, but not by a naive
split) in `ktpass`; some "Parameters"-titled tables are actually
subcommand *indexes* linking to other pages, not real flag tables
(`bitsadmin cache`); and multi-subsection pages repeat their table
header once per subsection using inconsistent column names ("Option"
instead of "Parameter"), which were being captured as fake flags
named after the header text itself (`bcdedit`).

### Add `windows-powershell-docs` as a single source covering four
    roadmap items at once

Reason: went looking specifically for an Active Directory PowerShell
module source and found it lives in a repo separate from
`PowerShell-Docs` (`MicrosoftDocs/windows-powershell-docs`) - checking
its actual directory listing (not just the `ActiveDirectory` folder
being searched for) showed ~140 Windows Server role modules total,
including `ScheduledTasks`, `NetSecurity` (Windows Firewall), and
DNS/DHCP/networking modules that had independently been on the
roadmap as separate Linux-adjacent-but-actually-Windows gaps. Curated
to 10 directly relevant modules (~695 cmdlets) rather than all ~140
(most - `ShieldedVMTemplate`, `HgsAttestation`, etc. - are far outside
this project's IT-ops scope). Reused the existing `powershell-md`
parser unchanged, since the format is identical to `PowerShell-Docs`.

### Add nftables via the systemd DocBook parser, generalized for
    combined short/long option syntax

Reason: nftables publishes its own DocBook XML manual
(`doc/nft.xml`), same format already supported for systemd - avoided
writing a new parser entirely. One real difference: systemd always
gives each flag alias its own `<term>` element (`-u` and `--unit=` as
two separate terms), while nftables writes combined forms in a single
`<option>` (`-h/--help`). Generalized the shared flag-extraction to
split on `/` when present, after confirming none of the 16 curated
systemd files use `/` inside a real `<term>` (a red herring
"-u/--unit=" match turned out to be inside cross-reference prose, not
an actual flag definition) - the change was safe for both sources.

### Build a new troff/man-page parser for cron, iptables, and ufw

Reason: these three tools (plus ssh, deferred) are the last major gap
identified in this project's IT-ops scope, and none of them publish
docs in any format already supported (Texinfo, Markdown, DocBook).
All three still use classic troff/man macros (`.TH`/`.SH`/`.TP`/`.B`,
inline `\fB.../\fP` font escapes) - the same underlying format across
independent upstream projects, so one parser investment covered all
three. Deliberately validated against all three together rather than
one at a time: `crontab` alone looked complete after 10/10 correct
extractions, but `iptables` and `ufw` immediately surfaced real format
variance (flag names as dedicated macro lines vs. inline escapes;
nested option lists inside a single flag's own description) that a
single-source validation would have missed and shipped as silent data
loss, mirroring the nested-table lesson already learned from
coreutils. iptables-extensions' ~200 match/target module docs
(highest remaining per-flag value) were left out of this pass - they
live in separate `.man` fragment files assembled via build-time
include markers, not full man pages, and need their own follow-up
investigation rather than reusing this parser's section-based
assumptions.

### Build a second, separate parser for mdoc rather than extending
    troff-man

Reason: OpenSSH's manuals looked at first glance like they might fit
the just-built troff-man parser (both are "classic Unix man page"
formats) - checking the actual source confirmed they don't. mdoc uses
a completely different, larger macro vocabulary (`.Sh`/`.Nm`/`.Bl`/
`.It Fl`/`.Ar`/`.Xr` vs. troff's `.TH`/`.SH`/`.TP`/`.B`/`\fB...\fP`),
and structurally places flags *inside* the DESCRIPTION section via a
`.Bl -tag` list rather than in a dedicated OPTIONS section, so even
the section-lookup logic wouldn't have transferred. Wrote a dedicated
`mdoc-man` parser reusing the same architectural lessons (depth-
tracked list nesting, paragraph accumulation) rather than the same
code. Validated against all 15 OpenSSH manuals together (not just
`ssh.1`) before trusting it, consistent with the troff-man validation
approach - this caught three real bugs (macro-composition leaking into
descriptions, word-collision corruption of ordinary prose, and a
list-closing bug) that a single-file validation would have missed.
Also extended the parser to recognize `.It Cm`/`.It Ic` (not just
`.It Fl`) so `ssh_config`/`sshd_config`'s config-file directives and
`sftp`'s interactive shell commands are captured as data too, not
just CLI flags - these are asked about just as often in practice.

### Add apt via the existing DocBook parser, build a new RST parser
    for dnf

Reason: apt and dnf were the last two entries on the original
tool-family gap list. apt publishes its own DocBook XML manuals (same
underlying format already supported for systemd/nftables) - reused
the shared parser unchanged except for one generalization: apt's
entity names contain dots and hyphens (`&apt-author.jgunthorpe;`,
`&synopsis-command-apt-get;`), which the original `\w+`-only entity
regex in `preprocess_docbook_xml` didn't match, leaving these entities
unresolved in the extracted text. Broadened the regex to
`[\w][\w.-]*` - safe because it only widens what counts as an entity
name, not what gets stripped. dnf, by contrast, publishes in
reStructuredText (double-backtick definition lists), a format with no
existing parser in this project - built one (`dnf-rst`) rather than
trying to bend an existing parser to fit. Two bugs surfaced during
validation against both target files: a comma-splitting bug where a
flag's own argument syntax (`--whatdepends
<capability>[,<capability>...]`) was mistaken for multiple comma-
separated flag aliases (fixed by only accepting comma-split pieces
that themselves start with `-`), and a two-part bug where `dnf.conf`'s
dash-less config directives (`cachedir`, `allow_vendor_change`) first
weren't recognized as valid entries at all (0 results), then - after
broadening recognition to accept bare identifiers - were still
discarded because the downstream flag-population code still
unconditionally applied a `-`-prefix filter written only for CLI
flags. Fixed by branching the extraction path: bare identifiers are
assigned directly, only dashed flag terms go through comma-splitting
and prefix filtering. 389 parameters recovered across the two sources'
4 files combined, closing the last originally-identified tool-family
gap; `dpkg` (POD format) was explicitly left as an optional,
lower-priority follow-up rather than pursued immediately, since most
Debian/Ubuntu day-to-day usage goes through `apt` rather than `dpkg`
directly.

### Fix apt/dnf's missing merge, then generalize the fix once it
    surfaced an older bug affecting ssh-keygen/apt-get/apt-cache/
    systemd-analyze too

Reason: after documenting the apt/dnf addition, checked (rather than
assumed) that the new records had actually merged with their tldr
counterparts the way every other complete-reference source does -
they hadn't. `apt-docs`/`dnf-docs` had been left out of
`COMPLETE_REFERENCE_SOURCES`, so the merge step never even considered
them; `apt`, `apt-get`, `apt-cache`, and `dnf` each existed as two
separate records instead of one (full parameters with zero examples on
one side, real examples with almost no parameters on the other).
Adding both sources to the tuple fixed the direct case, but checking
whether the same root cause reproduced elsewhere (rather than stopping
at the reported instance) found a second, older, unrelated bug: tldr's
parser converts every hyphen in a filename to a space unconditionally
- correct for real multi-word subcommands (`docker-compose` ->
"docker compose"), wrong for standalone binaries that are genuinely
typed with the hyphen (`ssh-keygen`, `apt-get`, `systemd-analyze`).
Since reference-source parsers (DocBook/mdoc) keep these hyphenated,
the tldr counterpart landed under a different, incorrect command name
and silently never merged - true since ssh-keygen and systemd-analyze
were first added, not something introduced today. Fixed at the merge
step rather than in the tldr parser itself, so the correct
space-conversion behavior for genuine subcommands wasn't touched:
before finalizing a hyphenated reference-only group, also look for a
same-named-but-spaced group made up entirely of tldr records and fold
it in. Total dropped slightly (162,294 -> 162,234) as orphaned
duplicate rows were absorbed into their correct merged record instead
of remaining separate.

### Capture DocBook tools' own subcommands as retrievable parameter-
    like records

Reason: after the apt/dnf merge fix, live-tested a related question -
`"what does systemd-analyze blame do?"` - and got an unrelated answer
back. The DocBook parser had always deliberately excluded subcommand
entries from `parameters` (they have a `<command>` term, not
`<option>`/`<varname>`), folding only their *names* into a one-line
summary sentence in the main description; their actual descriptions
were never stored anywhere. Found two different XML shapes needed
separate handling, not one: `systemctl`/`loginctl`/`timedatectl`-style
tools list subcommands as entries in a "Commands" `<variablelist>` -
extended the existing name-collecting loop to also grab each entry's
own `<listitem>` description; `systemd-analyze`-style tools instead
give each subcommand its own `<refsect2>`, titled with the full
invocation text, and have no "Commands" list at all - added a second
extraction path matching refsect2 titles that start with the page's
own command name. Deliberately reused the existing `parameters` list
(rather than inventing a new record type) since the existing
question-generation templates in `build_dataset.py` already phrase
naturally for this ("What does {command} {name} do?" reads correctly
for both a flag and a subcommand), and the existing bare-word
scoped-retrieval mechanism built for no-dash flag questions applies
without any changes - a subcommand name is just a bare token like `l`
in `"ls l"`, already handled generically. Verified live before and
after against `systemd-analyze blame`, `systemctl status`, and
`journalctl -f`, plus the full existing regression set. 754 new
training examples recovered (162,234 -> 162,988).

### Run a dataset-wide markup-leak audit at the ~163K milestone, fix
    the one real finding (mdoc escape sequences)

Reason: user asked, after two straight sessions of fixes, to check the
current ~163K-row dataset for empty/unused/broken filler data the way
earlier project milestones were audited. Wrote a battery of regex
scans for known leftover-markup signatures from every parser format
built in this project (texinfo `@macro`, DocBook tags, troff/mdoc
macros and escapes, RST backticks, Markdown headings, HTML tags,
raw pipe-tables) and ran them across the whole dataset, not just
today's sources. Deliberately verified every hit against full context
before trusting a count, since most were false positives baked into
the detection regexes themselves, not real bugs - `@example.com`
addresses matching a texinfo pattern, git's own `<placeholder>`
argument syntax matching DocBook tag names, triple-backtick fences
matching an RST pattern, shell `#` comments matching a heading
pattern. One held up: the mdoc parser (ssh/sftp/ssh-keygen/
ssh_config/sshd_config) never stripped ANY backslash escape sequence,
so several (`\&`, `\-`, `\e`, `\%`, `\(em`, `\*(Ge`...) leaked into
user-facing answers verbatim, and one nested macro (`Ql`, "quote a
literal") was missing from the known-macro-name set entirely, leaking
the literal word "Ql" into `ssh -e`'s answer. Fixed both, plus a
second spot where the same escape leaked through a different code
path (`mdoc_item_name` builds a flag/command name directly from a raw
token, bypassing `mdoc_clean_line` entirely). Two lower-value findings
were surfaced but deliberately NOT fixed: a small set of
`about_Comparison_Operators`-style PowerShell conceptual docs embed a
literal Markdown table inside what our extractor treats as flowing
prose (20 rows, would need actual table-to-prose conversion logic to
fix properly, not a simple strip); and 48 duplicate (instruction,
response) pairs where a handful of flags (`git grep -h`, `cp -r`,
`rm -r`...) are documented identically twice in their own source -
both are stable, pre-existing, and small enough (<0.03% of the
dataset combined) that chasing them now isn't worth it relative to the
one real bug found. Verified live via RAG before/after, plus the
existing regression set - zero rows added or removed, pure text
cleanup.

### Run a manual live-question review before retraining, on top of the
    automated audit

Reason: user explicitly asked, before committing to a `v1` retrain and
deleting old models, for a list of real questions per source so
responses could be checked directly - not another automated pass. Ran
35 questions spanning every major source live through `test_model.py`.
This caught two real, sizeable bugs the earlier markup-leak audit
never would have, since neither involved leftover formatting syntax:

1. `"what is the syntax of Get-Process?"` returned a bare `###
   ParameterSetName` heading with no actual syntax. Traced to a
   `build_dataset.py` cleanup regex meant to strip a real "###
   CommonParameters" doc heading, written with an overly permissive
   optional group that matched the word "CommonParameters" ANYWHERE in
   text - including the harmless `[<CommonParameters>]` syntax
   placeholder present in nearly every standard PowerShell cmdlet's
   own syntax block - deleting it and everything after, including the
   closing code fence. Affected 1,377 of 3,149 PowerShell records
   (44%). Fixed by anchoring the regex to only match when
   "CommonParameters" is the entire content of its own line.
2. `"what does git rebase -i do?"` returned a completely unrelated
   answer. Not a retrieval bug - `git rebase` had only 2 parameters
   captured total, and `-i` wasn't one of them. Root cause: git's own
   AsciiDoc option-parser only recognized backtick-wrapped flag terms
   (`` `--flag`:: ``), but 91 of git's `.adoc` files write flag terms
   bare, without backticks (`-i::`, `-e <pattern>::`) - 1,076 flag
   lines in this style, next to 1,873 backtick-wrapped ones, meaning
   roughly a third of git's own documented flags were invisible from
   the start. Fixed by accepting both styles. This also surfaced 102
   non-flag entries that had been reaching `parameters` under the old
   backtick-only path too (nested enum values for a parent flag's
   argument, and one garbled positional-argument placeholder) - since
   every real git flag starts with `-`, filtered anything that
   doesn't.

### Chase the git-flag bug to its actual root, not just the reported
    symptom - three more bugs found along the way

Reason: fixing "git rebase -i returns the wrong answer" surfaced that
`git rebase` had only 2 parameters total - a completeness bug, not a
retrieval bug. Investigating why kept finding more of the same root
problem rather than one isolated case, consistent with this project's
"one bug found by hand often points at a whole bug class" pattern:

1. My first fix (accepting bare, non-backtick flag terms) recovered
   1,076 flags but also let through 102 non-flag entries - nested
   value-options for a parent flag's own argument (e.g.
   `--word-diff[=<mode>]`'s `color`/`plain`/`porcelain` values,

   documented git subcommands (`git stash`'s `pop`/`push`/`apply`...)

   stripping character class, which cleanly empties the pure-garbage
   case and correctly recovers `mailmap` from `` `mailmap (<bool>)`::

   reliable syntactic signal distinguishes them from real subcommands

   labeled.
2. Investigating `git stash pop` specifically (still wrong after fix
   1) found git's own subcommands live in a separate `COMMANDS`

   dash-prefixed ones.

### Close the flush-left git-COMMANDS gap by rewriting the term parser
    instead of adding a third special case

Reason: user asked directly to fix the one known open issue left from
the previous pass (~53 subcommand entries in `git-remote`/
`git-worktree` using a flush-left description format the parser
couldn't handle). Rather than bolt on a third format-specific branch
next to "indented" and "blank-line-then-indented", rewrote the parser
to stop depending on formatting at all: find every term marker in a
section, and treat everything between one term and the next as its
description. This handles all three known variants in one pass and,
as a bonus, fixed a smaller pre-existing truncation bug too (AsciiDoc
`+`-continuation paragraphs, like the second half of
`git push --force`'s explanation, were previously cut off since only
indented lines were captured). Checking `git config` while validating
this found a second gap in the same family: some `COMMANDS` sections
write subcommand terms bare AND without a leading dash (`list::`, not
`` `list`::`` or a dashed flag), which neither existing branch of the
term-matching regex accepted at all. Broadening the pattern to accept
any non-backtick text ending in `::` immediately over-matched, because
AsciiDoc reuses that exact syntax for unrelated things within the same
sections (italicized argument placeholders, single-quoted terms,
escaped literals, and - most seriously - full example command lines
and interactive-menu descriptions that are not subcommand names).
Fixed with a two-part rule instead of reverting: strip AsciiDoc's
quote/italic wrapper characters and unescape `\-` first (recovers
`write`, `verify`, `--` correctly rather than discarding them), then
require any bare (non-dash) result to match a plain identifier pattern
- dash-prefixed terms are still always accepted, since real flags never
need this check. Checked for the same problem across the *entire*
git-docs source (not just the reported file) before calling it done,
per the project's standing rule to hunt the whole bug class rather
than patch the reported instance. Verified live and against the full
regression set. Dataset grew from 170,666 to 171,559.

### Fix a retrieval-layer command-matching bug found while verifying
    the audit's fixes, not the fixes themselves

Reason: after fixing nftables/dnf/git, several of the SAME questions
still returned wrong answers - but the correct rows now existed in
`dataset.jsonl`, proving the bug had moved from "missing data" to
"retrieval". Root cause: `find_mentioned_command()` sorted candidate
command names by length and returned the first match, with no tiebreak
for equal-length names - `nft` (3 chars) and `add` (3 chars, a real,
unrelated Windows CLI command) are the same length, so "what does nft
add rule do?" non-deterministically resolved to "add" instead of
"nft", scoping the whole search to the wrong command's data. Same
story for `dnf` losing to the real Windows `list` command. This bug
predates this session - the audit's own new questions just happened to
use verb-shaped words (`add`, `delete`, `list`) that are also real,
if small and unrelated, top-level commands, exposing something short
spot-checks with more distinctive vocabulary had never triggered.
Fixed by preferring whichever match starts EARLIEST in the question
text - the actual command is always named first in this project's
"what does X Y do?" phrasing, so position is a reliable, general
tiebreak, unlike length. Also found and fixed, in the same pass: a
`bare_flag()`-derived short-question ("what does dnf list do?" from
`--list`) that collided with the real `list` command's identically
phrased question, and a dead-code bug in a same-session fix attempt
(a new `elif mentioned_command:` branch was nested one level too deep,
inside `if is_flag_question:`, checking the same variable that had
already been tested false one line above - unreachable, so it silently
never ran). Fixing the dead-code bug then caused a real regression of
its own (an over-broad shortcut-keyword addition made the
well-established, previously-correct `F2` answer worse by narrowing
its search to a bad local match) - caught by re-running the full
regression set immediately after, not assumed safe. All verified live
before declaring done.

what they reveal about fixing this class of bug:

1. The `GENERIC_WORD_COMMAND_NAMES` fix (Windows' own `list`/`add`
   commands losing to this project's "can you **list** all X flags?"
   question template) is the mirror image of the tiebreak fix two

Reason: after the third audit closed with a list of confirmed gaps
(`net use` family, `apt-key`, five systemd CLI tools, ten missing
keyboard shortcuts), user asked to fill them in by finding sources
online rather than treating the list as final. This tested the

Outcome, gap by gap:

### Prepare for a public GitHub upload (2026-08-13)

User wants to publish this repository, including the generated dataset
and model artifacts (not just the code), and explicitly wants to avoid
legal trouble. Since the dataset is built from third-party
documentation (git, coreutils, grep, Docker, systemd, nftables, cron,
iptables, ufw, OpenSSH, apt, dnf, Microsoft docs, tldr), each under its
own license (mostly GPL-2.0/3.0, GFDL 1.3, LGPL-2.1, CC-BY 4.0, Apache
2.0, ISC, or BSD-style - verified directly by reading each source's own
COPYING/LICENSE file rather than assuming), the code's own MIT choice
can't cover the dataset - claiming otherwise would be actively
misleading, not just legally risky.

Researched real precedent rather than reasoning from first principles
alone: **Thomson Reuters v. ROSS Intelligence** (Feb 2025, on appeal)
is the closest analogous case - a court rejected fair use for
extracting short text units (headnotes) from documents to build an
AI/retrieval system, but critically, Thomson Reuters' content was
proprietary with zero reuse rights, unlike this project's sources
which are already openly licensed and grant reuse under specific
conditions. **Feist v. Rural Telephone** (1991) confirms raw facts
(command/flag names) aren't copyrightable, but doesn't extend that
protection to descriptive prose copied from a source. The "does GPL
propagate to AI model weights" debate has no legal consensus either
way. None of this yields a "zero risk" answer - explicitly told the
user this isn't legal advice and true certainty needs an actual
lawyer - but it informed a concrete, reasonable-effort mitigation
instead of either ignoring the issue or over-promising safety:

-   `LICENSE` (MIT) added, explicitly scoped to the author's own code
    only, with a note pointing to `ATTRIBUTION.md` for everything else
    - rather than a blanket MIT claim that would misrepresent
    ownership of content that isn't the author's to relicense.
-   `ATTRIBUTION.md` added, mapping every one of the 17 sources to its
    real license (traced through `commands.json`'s `path` field back
    to `data/raw/<source>`), plus the base model's (Qwen2.5-0.5B-
    Instruct, Apache 2.0, confirmed via its Hugging Face model card
    rather than assumed).
-   `THIRD_PARTY_LICENSES/` added with unmodified copies of each
    license's actual text (GPL-2.0/3.0, GFDL-1.3, LGPL-2.1, ISC,
    Apache-2.0, CC-BY-4.0, BSD) - copied verbatim from the already-
    cloned source repos (or fetched directly from gnu.org for LGPL-2.1,
    which wasn't present in the local systemd clone), not
    reconstructed from memory. GFDL specifically requires the license
    itself be included unmodified, so this wasn't optional for the two
    GFDL sources (coreutils, grep).
-   Decided **not** to publish `qwen-it-mentor-v6` even though it
    wasn't deleted for licensing reasons per se - since it's already
    unreachable dead weight (see the entry above), publishing it would
    only add a second, murkier layer of legal uncertainty (does a
    fine-tune trained on copyleft-derived text carry any obligation
    into its weights - unresolved in current case law) for zero
    functional benefit.
-   `.gitignore` added excluding `data/raw/` (the raw clones
    themselves - regenerable via `scripts/download_sources.py`, and
    republishing full copies of these repos verbatim inside another
    repo was never the goal, independent of licensing).

Separately, while preparing the repo: deleted every old model
checkpoint under `models/` (all confirmed unreachable, see above) and
`scripts/train.py` (LoRA retraining was already decided against), and
trimmed `peft`/`trl`/`datasets`/`accelerate` out of `requirements.txt`
since `train.py` was their only consumer - not a licensing decision,
just removing dead weight while already touching the repo structure
for the same publish-prep pass.

### Fix `mentor_core.load()` hanging with no internet, despite the
    "offline after first run" promise never actually being enforced
    (2026-08-14)

Reason: user reported the desktop app getting stuck at "Loading search
index..." with the internet disconnected - directly contradicting
`README.md`'s stated design ("first run downloads the models,
subsequent runs are fully offline"). Root cause: `load()` never told
`transformers`/`sentence_transformers`/`huggingface_hub` to skip the
network. Even with every model file already cached locally,
`SentenceTransformer(...)`/`AutoTokenizer.from_pretrained(...)`/
`AutoModelForCausalLM.from_pretrained(...)` still make a request to
Hugging Face Hub to check for a newer revision before falling back to
cache - with no internet, this request hangs until it times out
instead of failing fast, which is what looked like a frozen "Loading
search index..." label (the real hang was one step later, in loading
the embedding model, but no progress message existed for that step
yet - added one while fixing this).

First fix attempt was itself wrong and shipped without live-testing
against the actual reported symptom: set the `HF_HUB_OFFLINE`/
`TRANSFORMERS_OFFLINE` environment variables inside `load()` before
each model call. This does nothing - `transformers`/`huggingface_hub`
read those variables once, at their own **import** time, which happens
at the top of `mentor_core.py`, long before `load()` ever runs and
sets them. Setting an env var after the library that reads it has
already imported has no effect; the user re-tested with the internet
off and confirmed it was still stuck in the same place. Fixed properly
by passing `local_files_only=True` directly to each `from_pretrained`/
`SentenceTransformer` call instead - a real per-call function argument,
read fresh every time, not cached at import. Wrapped in a small
`_load_with_offline_fallback()` helper: try `local_files_only=True`
first (works instantly if the cache has the files, raises `OSError` if
not); only fall back to `local_files_only=False` (network allowed) if
that happens, which is the genuine first-run-ever case - preserving
the "first run needs internet" half of the original design while
finally actually delivering the "then fully offline" half.

Verified end-to-end, not just by reading the diff (per this project's
verification standard): ran `mentor_core.load()` directly against the
installed environment with `local_files_only=True` at every call site -
embedding model loaded from cache in 2.47s, tokenizer+base model in
under 2s combined, full `load()` in 4.88s total, then a real question
(`"what does grep -i do?"`) answered correctly - all with zero network
calls attempted, confirming the fix actually works rather than assuming
it does because the first (wrong) version looked plausible too.
